## 1. 目标与非目标

### 目标

- 在 Cloudflare **免费额度内**长期运行，不产生任何费用
- 支持多软件、多套餐、自定义前缀
- 爱发电付款后**自动发码**，买家无需等待人工
- 授权信息由服务端掌控，客户端无法伪造
- 续费不换 key，换机可自助解绑，减少售后

### 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 离线软件的强保护 | 客户端可被 patch，收益低于成本 |
| 并发会话检测 | 设备数上限已覆盖其价值 |
| 用量配额管理界面 | 业务形态未定，只留字段 |
| custom_order_id 自动绑定 | 增加复杂度，正常流程不需要 |
| 平台随机回复发卡 | 无法续旧 key，与核心策略冲突 |
| L1 模式（URL 直带 key） | 面向通用订阅客户端，非当前业务 |

## 2. 名词定义

这几个词在本文档中有严格含义，不要混用：

| 名词 | 含义 | 频率 | 是否计费 |
|---|---|---|---|
| **验证（verify）** | 客户端用 `key + 设备指纹` 调 `/api/v1/verify` 换取令牌 | 每天 2–5 次 | ✅ 计 1 次请求 |
| **令牌（token）** | 验证成功后服务端签发的 RS256 JWT | 缓存 12–24h | ❌ 本地校验不联网 |
| **业务调用** | 软件实际功能请求云端 | 视业务而定 | 若业务不在 CF 则不占额度 |
| **心跳** | 定时回连保活 | — | **不存在此机制** |

> **「每 key 每日 N 次验证」= 同一天内该 key 最多换取 N 枚令牌。**
> 它防的是「脚本刷接口烧额度」，不是防盗版（防盗版靠设备绑定）。

## 3. 架构

```
                    ┌─────────────────────────────┐
                    │  授权中心 Worker             │
   客户端 ──HTTP──→ │  /api/v1/*   /webhook/*     │ ← 出口①③
   外部服务 ─HTTP─→ │  /admin/*   (Access 保护)    │
   同账号 Worker ──→ │  (Service Binding RPC)      │ ← 出口②
                    │         ↓                   │
                    │        D1                   │
                    └─────────────────────────────┘
```

### 三个调用出口（共用同一套校验核心）

| 出口 | 调用方 | 凭证 | 成本 |
|---|---|---|---|
| ① HTTP | 客户端软件 | `key` + 设备指纹 | 1 次请求 |
| ② RPC | 同账号 Cloudflare Worker | Service Binding（无需凭证） | **0 成本**，不计请求额度 |
| ③ HTTP | 外部服务器（VPS 等） | `apps.server_key` | 1 次请求 + 建议本地缓存 5 分钟 |

> 官方确认：Service Bindings 不增加费用。但**用公网 URL 互调会双倍计费**，必须用绑定。

### 部署形态

| 项 | 值 |
|---|---|
| 域名 | `key.example.com`（自定义域名必须，Access 依赖） |
| 静态资源 | Workers Static Assets，**请求免费且不限量** |
| 数据库 | D1（免费 10 万写/天、500 万读/天、5 GB） |
| 定时任务 | Cron `*/10 * * * *` |
| 管理鉴权 | Cloudflare Access（`/admin*`）+ 口令兜底 |
| 成本 | **¥0** |

## 4. 授权模型（五维取三）

| 维度 | 取值 | 状态 |
|---|---|---|
| **时间** | `lifetime` 永久 / `fixed` 固定到期 / `from_activation` 首激活 N 天 / 可续期叠加 | ✅ 实现 |
| **功能** | `features` JSON 功能位，如 `{"pro":true,"export":false}` | ✅ 实现 |
| **设备** | 绑定上限 N 台，可踢设备，可自助解绑 | ✅ 实现 |
| **用量** | `quota_daily` / `quota_total` | ❌ 未实现（schema 中也没有这两列） |
| **并发** | — | ❌ 不做 |

### 时间维度细则

| 模式 | `activated_at` | `expires_at` | 说明 |
|---|---|---|---|
| `lifetime` | 可空 | `NULL` | 永久有效 |
| `fixed` | 可空 | 生成时确定 | 到点即止，不因激活变化 |
| `from_activation` | 首次验证时写入 | 激活时 = `activated_at + N天` | 未激活时 `expires_at` 为 `NULL` |

## 5. Key 设计

```
格式：  PREFIX-XXXX-XXXX-XXXX-XXXX-XXXX-C
字符集：Crockford Base32 —— 0123456789ABCDEFGHJKMNPQRSTVWXYZ
        （剔除 I / L / O / U，防手抄与口述歧义）
随机体：20 位 = 100 bit 熵，暴力枚举不可行
校验位：Luhn mod 32，对「前缀 + 随机体」整体计算
```

示例：`DEMO-A1B2-C3D4-E5F6-G7H8-I9J0-K`

### 为什么校验位对整体计算

生成时前缀长度不固定，校验时无法可靠切分前缀与随机体。因此**把前缀也纳入 Luhn 计算范围**，校验时对整串（除末位）计算即可，无需知道前缀长度。

### 存储双字段

| 字段 | 用途 |
|---|---|
| `key` | 展示格式，带分隔符，用于导出和显示 |
| `key_norm` | 去掉所有分隔符，**建唯一索引、用于查询** |

> 原因：用户输入的分隔符位置可能不同（`DEMO-XXXX` vs `DEMOXXXX`），用归一化字段查询才不会漏。

### 校验位的前端价值

输错一位时客户端本地就能判定格式错误，**不打服务器**。这直接省掉了大量无效请求。

## 6. 令牌设计

| 项 | 设计 |
|---|---|
| 算法 | **RS256**（选择理由：C# / Java / Kotlin / Python 全部原生支持，不赌冷门库） |
| 载荷 | `ver`(版本) `iss` `sub`(license_id) `app` `plan`(plan_id) `features`(功能位) `max_devices` `fingerprint`(指纹哈希) `duration_mode` `iat` `exp` |
| TTL | 12–24 小时（可配 `TOKEN_TTL_HOURS`） |
| 存储位置 | **客户端内存，进程退出即丢弃** |
| 客户端能力 | 只持公钥，**只能验签，不能签发** |

### 为什么不加密令牌

- **加密解决「看不见」，签名解决「改不了」。** 攻击者不需要读懂令牌，直接转发即可使用，加密无效。
- 对称加密要求客户端持有密钥 → 密钥可被提取（dnSpy / jadx 十分钟），等于没加密。
- 令牌内无敏感信息（只有 ID、功能位、到期时间），没有隐藏必要。

### 为什么不设短 TTL

短 TTL 会**强制客户端续期**，等于变相心跳。按 1000 用户 × 96 次/天估算，直接把 10 万额度打满 96%。

安全性靠**设备指纹在服务端比对**，不靠时间短：

> **别用「时间短」换安全，用「绑指纹」换安全。前者花额度，后者不花。**

### 「随用随没」的收益

令牌只在内存中，进程退出即消失，无法复制到其他机器长期使用。这比长有效期+本地持久化安全得多，同时 TTL 又能给足，零心跳。

## 7. 生命周期

| 场景 | 行为 |
|---|---|
| **首次购买** | 生成新 key |
| **续费** | 按 `buyer_id + app_id` 找旧 key → **累加时长，不生成新 key** |
| **旧 key 已过期** | 取最近一条「复活」，从**当前时间**起算（不是从过期时间） |
| **key 泄露** | 封禁 + **换发**（继承时长/功能/设备上限/买家信息，**清空设备绑定**） |
| **换机** | 查询页自助解绑全部设备，**30 天限一次** |
| **到期** | 状态由 `expires_at` 算出，不靠定时任务翻状态 |

### 续费匹配顺序

```
同软件 + 同爱发电 buyer_id
  ↓ 有未过期的 → 取最近创建的那条续期
  ↓ 没有 → 取最近一条已过期的复活并累加
  ↓ 都没有 → 生成新 key
```

> 目标：**一个用户在一个软件下永远只持有一个 key**，避免越积越多。
> 局限：买家换爱发电账号购买时无法识别，此为平台数据限制，无解。

### 为什么换发要清空设备

换发场景通常是泄露或账号异常，原设备不可信，必须重新绑定。旧 key 置 `revoked` 而非删除，保留历史可查。

## 8. 发码链路

```
爱发电付款
   ↓
POST /webhook/afdian
   ├─ RSA 验签：out_trade_no + user_id + plan_id + total_amount
   │  ⚠️ sign 在 data.order.sign（不是顶层），取错位置会导致全部推送被拒
   ├─ status == 2 才处理
   ├─ 幂等：out_trade_no 为主键
   ↓
匹配套餐（sku_id 优先 → plan_id 兜底）
   ↓ 未匹配 → delivery = 'unmatched'，进对账页手工处理
   ↓
有旧 key → 续期 ／ 无 → 新建
   ↓
写入 msg_queue（pending）
   ↓
waitUntil 立即发私信 ／ 失败由 Cron 重试（最多 5 次）
   ↓
限频：爱发电私信 10/s、1000/h，Cron 每次只处理 12 条
```

### 赞助（订阅）与商品（售卖型）的区别

爱发电有两套完全不同的售卖形态，字段和语义都不同：

| | 赞助 / 订阅方案 | 商品 / 售卖型 |
|---|---|---|
| `product_type` | `0` | `1` |
| 识别字段 | `plan_id` | `sku_detail[].sku_id` |
| 库存 | 无 | 有（`stock`） |
| 型号 | 无（订阅方案没有 `skus` 字段） | 有，每个型号独立价格与库存 |
| 付款节奏 | 可能每月自动扣款，天然走「续费续旧 key」 | 一次性买断 |

本地用 `plans.afdian_type`（`plan` / `sku`）区分。匹配时：
- 先按 `sku_id` 找，且只匹配 `afdian_type='sku'` 的套餐
- 再按 `plan_id` 找，且只匹配 `afdian_type='plan'` 的套餐

这样避免同一个套餐被两种渠道误匹配。

**多型号订单的处理**：捆绑包/多 SKU 订单只会按**第一个型号**发码，并在 `orders.delivery_error` 写一条「多型号订单（N 个）」的提示，对账时能看到黄色警告。不做拆分发放——拆分会让发码逻辑复杂化，而捆绑包是少数场景。

### 取码页（claim）

**不显示 key**，只做「重发私信」：

```
用户输入订单号 → 系统查订单 → 把 key 重新私信给该订单对应的爱发电账号
                            → 页面只显示「已发送到你的爱发电私信」
```

**设计理由**：订单号含日期时间，可被推测。若页面直接显示 key，猜中订单号即等于盗号。改成只触发重发后，攻击者猜中订单号得到的唯一结果，是**真实买家收到一条重复私信**，自己什么也拿不到。

### 对账补单

Cron 每 10 分钟调 `query-order`。翻页策略当前基于「本页该处理的订单是否都已存在」：
（注：`query-order` 实际**返回** `create_time`，改为时间游标更稳，属待优化项。）

```
拉第 1 页 → 一次查出本页哪些订单本地已存在
  ├─ 整页都已存在 → 说明已追平历史，停止
  └─ 有缺失 → 逐条 processOrder 补发，继续下一页（上限 10 页）
```

> 常态下只拉 1 页、命中即停，成本 = 1 次 API + 1 次 D1 读，每天约 144 次。
> 断一整天时会自动翻页补齐，不会漏。
> 另外管理台提供「从爱发电同步」按钮，可手动触发同一套逻辑。

### 三种补发出口（应对网络问题）

| 情况 | 现象 | 处理 |
|---|---|---|
| webhook 完全没收到 | 爱发电有单，本地无记录 | 订单页「从爱发电同步」或等 Cron |
| 私信发送失败 | 订单投递状态 = 失败 / 待发送 | 订单页「重发」，Cron 也会自动重试 5 次 |
| 已发送但买家没收到 | 投递状态 = 已发送 | 订单页「重发」会**强制重新入队并发一条**，不受原状态限制 |

## 9. 接口清单

### 公开（无需鉴权）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/verify` | 验证 key，返回令牌 |
| POST | `/api/v1/status` | 查询状态（key 显示掩码） |
| POST | `/api/v1/unbind` | 自助解绑（30 天冷却） |
| POST | `/api/v1/claim` | 凭订单号触发私信重发 |
| POST | `/api/v1/server/check` | **服务端校验**（业务服务器调用，凭证 `server_key`） |
| GET | `/api/v1/pubkey` | 获取验签公钥 |
| POST | `/webhook/afdian` | 爱发电回调（RSA 验签） |

> `/verify` 给客户端用，返回签名令牌；`/server/check` 给业务服务器用，只回答「能不能用」，不签发任何凭证。
> 两者凭证不同：客户端用 `key`，服务器用 `apps.server_key`，客户端永远拿不到后者。

### 管理（Access 保护）

`/admin/api/*` —— 登录、概览、软件、套餐、授权码、批量生成、导出、续期、换发、封禁、设备踢出、订单、批次、设置、公钥、日志。

### 验证接口返回码

| code | 含义 |
|---|---|
| `OK` | 成功，返回 token |
| `INVALID_KEY` | 格式或校验位错误 |
| `NOT_FOUND` | 不存在 |
| `EXPIRED` | 已过期 |
| `BANNED` / `REVOKED` | 封禁 / 吊销 |
| `DEVICE_LIMIT` | 设备数超限 |
| `APP_MISMATCH` | 不属于该软件 |
| `VERIFY_LIMIT` | 当日验证次数超限 |
| `SERVICE_BUSY` | 额度熔断中 |

> 业务级失败统一返回 **HTTP 200 + `ok:false`**，避免客户端库把 4xx 当网络错误处理。

## 10. 限流与额度保护

### 免费额度硬约束

| 资源 | 额度 | 设计对策 |
|---|---|---|
| Worker 请求 | **10 万/天，账号级**（拆 Worker 不叠加） | 长 TTL、零心跳、`pubkey` 走 CDN 缓存 |
| CPU | 10 ms/请求 | 批量生成单请求限 200 且分批 50 条写入 |
| D1 写入 | 10 万行/天 | 设备 `last_seen` 跨天才写；一次请求最多写一行 |
| D1 读取 | 500 万行/天 | 充裕 |
| 静态资源 | **免费不限量** | 所有页面、CSS、JS 都走 Assets |

**写入是真正的瓶颈**：每次 `verify` 至少写 1 行（`verify_count` 原子扣减），请求额度与写额度 1:1 同步耗尽。
按每人每天 3 次验证估算，天花板约 **3.3 万日活**。若需提升，把 `verify_count` 改为每 5 次落库一次即可（精度 ±5，对 100 次上限足够）。

**数据保留策略**（Cron 每天执行一次）：

| 表 | 保留 | 原因 |
|---|---|---|
| `msg_queue` | 30 天（仅已发/失败） | 长期堆积会拖慢 `state='pending'` 扫描 |
| `audit_logs` | 90 天 | 查询变慢，且占存储 |
| `req_counter` | 30 天 | 只用于当日熔断判断 |

> 额度每天 UTC 0 点（北京时间 08:00）重置。最坏情况是「当天剩余时间不可用」，不会整月瘫痪。

### 性能与 CPU 实测

单次操作耗时（Node + OpenSSL 实测，Workers 用 BoringSSL，同量级）：

| 操作 | 单次耗时 | 备注 |
|---|---|---|
| key 格式校验（含 Luhn 26 次循环） | **0.8 µs** | |
| MD5（爱发电 API 签名） | **2.8 µs** | 仅 webhook / 对账时 |
| SHA-256（令牌内设备指纹） | **22.8 µs** | 每次 verify 一次 |
| RS256 签名 | **614 µs** | verify 的绝对大头，占 96% |

**单次 verify ≈ 0.64 ms**，上限 10 ms/请求，**余量约 16 倍**。流量涨 10 倍也不会撞 CPU 限制。

D1 查询是 IO 等待，**不计入 CPU**，但决定接口延迟（每次往返约 10–50 ms）：

| 接口 | 往返次数 |
|---|---|
| `verify`（稳态） | **3** |
| `verify`（首次激活） | **4** |
| `server/check` | **2**（0 写入） |
| `status` | 2 |
| `webhook` | 6–8（非热路径） |
| Cron 对账 | 每页 1 + 每单 6–8，**单轮上限 40 单** |

已做的优化：

| 优化 | 效果 |
|---|---|
| verify 的「设备写入 + 首激活」合并成一次 `batch` | 少 1 次往返 |
| 设备超限检查提到验证计数之前 | 失败请求不消耗计数 |
| `stats` 6 个查询改 `Promise.all` | 概览页延迟从 6×往返 降到 1×往返 |
| 单条查询去掉 `id = ? OR key_norm = ?` | 避免 OR 退化成扫描，先走主键 |
| 对账单轮上限 40 单 | 防止补几百单撞 Cron 时长上限 |
| `todayStr` 缓存 60 秒 | 热路径不再每次构造 Date |
| `gate()` 白名单提为模块常量 | 每请求少一次数组分配 |
| 审计日志统一走 `audit()` | 消除 9 处重复 SQL |

### 三层限流

| 层 | 手段 | 挡什么 | 是否花额度 |
|---|---|---|---|
| ① 边缘 | WAF 限流规则（免费仅 **1 条**，10s/同IP） | 暴力刷接口 | ❌ 不花 |
| ② Worker 内 | 内存限流（per-isolate） | 单客户端滥用 | ✅ 已计费 |
| ③ 业务 | 每 key 每日验证上限 | 脚本刷、倒卖令牌 | ✅ 已计费 |

> 只有第 ① 层能省钱。第 ②③ 层请求已经计费，作用是止损与风控。

### 第 ② 层的三档配置（管理台可调）

参数不写死在代码里，存在 `meta.rate_profile`，内存缓存 60 秒。改完 1 分钟内生效，不用重新部署。

| 项 | 宽松 | 标准（默认） | 严格 |
|---|---|---|---|
| 验证 `/verify`，每 IP 每分钟 | 300 | **120** | 60 |
| 查询 `/status`，每 IP 每分钟 | 60 | 30 | 15 |
| 取码 `/claim`，每 IP 每 10 分钟 | 40 | 20 | 10 |
| 解绑 `/unbind`，每 IP 每小时 | 20 | 10 | 5 |
| 服务端校验 `/server/check`，每 IP 每分钟 | 600 | 300 | 150 |
| **输错授权码（坏 key）** | **20** | **20** | **20** |

最后一行是刻意固定的：**它不随档位变化**。原因是这一道挡的是扫描器（构造格式合法但不存在的 key 反复试探），而正常人一分钟不会输错 20 次。把它做进档位，用户只会往大调，一调大这道闸就等于不存在，单 IP 一天能刷 17 万次、直接吃穿 10 万请求额度。

**为什么不给自由填数字**：用户不知道 120 是宽松还是严格；填小了会立刻误伤所有用户且不会马上发现。三档 + 界面直显数值，是「可调」和「不会把自己搞挂」之间的平衡点。

**拦截次数统计**：每次被挡在内存 +1，每 10 次落库一次（`meta.rl_blocked:YYYY-MM-DD`），避免统计本身吃掉写额度。设置页显示「今日已拦截 N 次」——一直是 0 说明没人在刷；持续增长说明该收紧一档。

### 每 key 每日验证上限

| 项 | 值 |
|---|---|
| 默认 | **100 次/天**（正常用量 2–5 次的 20 倍以上，不会误伤） |
| 超额 | 返回 `VERIFY_LIMIT`，次日重置 |
| 可配 | 套餐级 `verify_limit`，0 = 不限 |
| 实现 | 条件 UPDATE 原子扣减，一次写入零读取 |

> 早期方案曾定 30 次，实测评估后调高：软件崩溃重试可能连续触发，30 次会误伤。

### 额度熔断分级（已实现）

实现方式：无法实时读取 Cloudflare 用量，因此**自己数**——内存累加、每 500 次落库一次（精度 ±500，对 10 万阈值足够）。分级结果缓存 60 秒，避免每请求读库。

| 用量 | P0 webhook | P1 验证 | P2 管理台 |
|---|---|---|---|
| < 70% | 正常 | 正常 | 正常 |
| 70–92% | 正常 | 正常 | 限流（仅 `stats`/`quota`/`me` 放行） |
| 92–97% | 正常 | **拒绝**（`SERVICE_BUSY`） | 拒绝 |
| > 97% | **正常** | 拒绝 | 拒绝 |

> **webhook 永远不掐**——丢单是收入损失，比「用户暂时激活不了」严重得多。
> 额度耗尽期间 webhook 仍返回 `{"ec":200,"em":""}`，订单靠次日对账补发。

## 12. 已知取舍

| 取舍 | 代价 | 为什么接受 |
|---|---|---|
| key 明文存储 | 库泄露即全泄露 | 需要导出 CSV 发买家；靠后台鉴权 + 审计兜底 |
| 令牌可被内存提取 | 提取后可用至 TTL 到期 | 绑设备指纹，服务端比对，提取也无用 |
| 封禁最长延迟一个 TTL | 最长 24h 内仍可用 | 可缩短 TTL 或加黑名单，权衡后不做 |
| 买家换账号无法识别续费 | 会生成新 key | 爱发电不提供跨账号身份，无解 |
| 不做并发检测 | 同 key 可多机轮换 | 设备数上限已限制同时绑定数 |
| 管理台不适配手机 | 手机上难以操作 | 批量操作本来就在桌面完成 |
